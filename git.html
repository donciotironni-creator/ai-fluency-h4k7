Cum lucrăm cu Git

Bune practici de echipă, în română. Folosim GitHub, dar principiile sunt aceleași peste tot — Git e Git; GitHub e doar locul unde stă remote-ul și unde facem pull request-urile. Scopul: istoric curat, munca nimănui pierdută, toți lucrăm la fel.

01 Modelul mental

Patru concepte și cam atât. Fără ele, restul e magie neagră.

  • Repository (repo) — folderul proiectului plus toată istoria lui. Copia ta locală e completă, nu o vedere parțială.
  • Commit — o fotografie a proiectului la un moment dat, cu un mesaj și un părinte. Istoricul e un lanț de commit-uri.
  • Branch — un pointer mișcător către un commit. Nu copiază fișiere; e o etichetă care avansează pe măsură ce comiți. De asta branch-urile-s ieftine.
  • Remote (origin) — copia de pe GitHub. push trimite commit-urile tale acolo; pull le aduce pe ale celorlalți.
Pentru echipa SQL: un commit e ca un BACKUP cu timestamp și comentariu. Un branch e ca un environment izolat. merge e ca un MERGE — împaci două stări. Diferența: în Git te poți întoarce oricând la orice snapshot, gratis.

02 Modelul de branching

Ținem simplu: trunk cu feature branches scurte.

  • main (sau master/develop, după repo) e sacru. Nu comiți direct pe el — se ajunge acolo doar prin pull request.
  • Pentru orice bucată de lucru îți faci un branch pornit din main la zi.
  • Branch-urile trăiesc scurt — ore sau zile, nu săptămâni. Cu cât stă mai mult deschis, cu atât doare mai tare merge-ul final.

Convenție de denumire

Prefix + descriere kebab-case, opțional ID de ticket:

feature/timeoff-accrual-policy
fix/filnet-ocr-null-date
hotfix/iris-deadlock-sync-job
chore/bump-dependencies
feature/PROJ-142-remaining-days   # cu ticket
Regula de aur: un branch = o intenție. Dacă te trezești că faci „și încă un fix cât tot aici", probabil e alt branch.

03 Commit-uri: mici, atomice, cu mesaj care spune DE CE

Un commit bun e o unitate logică ce are sens singură. Nu „munca de azi", ci „adaug validarea pe câmpul X".

Anatomia unui mesaj — Conventional Commits

<tip>: <ce face, la imperativ, sub 72 de caractere>

<corp opțional: DE CE, nu CUM — codul spune deja cum>

<footer opțional: refs ticket, breaking changes>

Tipuri folosite:

feat funcționalitate nouă fix bug docs documentație refactor rescriere fără schimbare de comportament chore mentenanță / config

Bun

feat: add remaining-days calculation for partial accrual

Accrual-ul lunar trebuia proratat pentru angajații intrați
la mijlocul lunii. Înainte primeau luna întreagă.

Refs: TIMEOFF-142

Anti-pattern

update                     # ce ai updatat?
fix bug                    # care bug?
asdf                       # ...
final version FINAL v2     # nu.
  • Commit des, local. E gratis. Poți rescrie istoricul înainte de push.
  • Fiecare commit lasă repo-ul într-o stare validă — compilează, trec testele.
  • Verifică ce comiți. git status și git diff --staged înainte de fiecare commit. Nu da git add . orbește — folosește git add -p.

04 Bucla zilnică

Workflow-ul standard, cap-coadă.

# 1. Pornești de la main la zi
git checkout main
git pull

# 2. Îți faci branch-ul de lucru
git checkout -b feature/timeoff-accrual-policy

# 3. Lucrezi. Comiți în bucăți logice.
git add -p                       # stage selectiv, pe bucăți
git commit -m "feat: ..."

# 4. Ții branch-ul sincronizat cu main (dacă lucrarea durează)
git fetch origin
git rebase origin/main

# 5. Împingi pe GitHub
git push -u origin feature/timeoff-accrual-policy

# 6. Deschizi Pull Request din GitHub UI
# 7. După aprobare + merge: cureți
git checkout main
git pull
git branch -d feature/timeoff-accrual-policy
git add -p te plimbă prin fiecare bucată de modificare și te întreabă dacă o incluzi. Așa ajungi la commit-uri atomice fără efort.

05 Pull Requests pe GitHub

PR-ul e locul unde codul devine al echipei. Nu e o formalitate — e review și e documentație.

Ce face un PR bun

  • Titlu clar — ca un mesaj de commit: feat: accrual proratat pentru intrări la mijloc de lună.
  • Descriere care răspunde la 3 întrebări: ce face? de ce (ce ticket)? cum verifici?
  • Mic. Un PR de 200 de linii primește review real. Unul de 2000 primește „LGTM 👍" fără să-l citească nimeni. Dacă e mare, sparge-l.
  • Self-review întâi. Citește-ți propriul diff în GitHub înainte să ceri altcuiva. Prinzi jumătate din observații singur.
  • Reviewers potriviți — cine cunoaște zona. Pentru module sensibile, reviewer-ul e obligatoriu.

Șablon de descriere PR

## Ce
Prorează accrual-ul lunar pentru angajații intrați la mijlocul lunii.

## De ce
Bug raportat de HR: angajat intrat pe 20 primea 1.75 zile în loc de ~0.58.
Refs: TIMEOFF-142

## Cum verific
1. Creează un angajat cu data de start 2026-06-20
2. Rulează jobul de accrual pentru iunie
3. RemainingDays trebuie proratat, nu luna întreagă

## Atenție la
Calculul din AccrualService.ComputeMonthly — logică de business.

Merge din PR

  • Squash and merge pentru branch-uri cu istoric zgomotos (multe „wip") — main rămâne o linie curată, un commit per feature.
  • După merge, șterge branch-ul de pe GitHub. Nu lăsa cimitire de branch-uri.

06 Merge vs. Rebase

Amândouă aduc modificările din main în branch-ul tău. Diferența e ce fac cu istoricul.

  • merge — creează un „merge commit" ce leagă cele două linii. Istoric fidel, dar cu multe furci.
  • rebase — mută commit-urile tale ca și cum ai fi pornit chiar acum din vârful lui main. Istoric liniar, curat.
Regula noastră: rebase pe branch-ul tău local, cât timp e doar al tău. Nu rebase pe nimic pe care l-ai împărțit cu alții.
# Îți sincronizezi branch-ul propriu cu main — OK
git fetch origin
git rebase origin/main
Interzis: rebase sau push --force pe main/develop/master ori pe orice branch pe care lucrează și altcineva. Rescrii istoria de sub picioarele lor. Dacă chiar trebuie să forțezi pe branch-ul TĂU după rebase, folosește git push --force-with-lease — niciodată --force simplu.

07 Ce NU comiți NICIODATĂ

Critic pentru o echipă care lucrează cu baze de date.

  • Connection string-uri (Server=...;Password=...) — în config local / secret manager, nu în repo.
  • Parole, API keys, token-uri, certificate.
  • Dump-uri de date reale — mai ales cu date de clienți / pacienți (GDPR).
  • Fișiere generate — bin/, obj/, node_modules/, build output.
  • Fișiere de IDE / OS — .idea/, *.user, Thumbs.db.

Toate stau în .gitignore, comis de la început:

# Build
bin/
obj/
node_modules/

# Secrete / config local
appsettings.Development.json
*.local.json
.env

# IDE / OS
.vs/
.idea/
*.user
Thumbs.db
Dacă ai comis deja un secret: nu e destul să-l ștergi într-un commit nou — rămâne în istoric. Trebuie rotit (schimbat) secretul și curățat istoricul (git filter-repo sau BFG). Mai bine să nu ajungi acolo.

08 Conflicte de merge

Un conflict înseamnă că două branch-uri au schimbat aceleași linii. Git nu ghicește — te întreabă pe tine. Nu intra în panică.

<<<<<<< HEAD
codul tău
=======
codul de pe main
>>>>>>> origin/main
  1. Deschizi fișierul, ștergi marcajele <<< / === / >>> și lași varianta corectă (uneori o combinație).
  2. git add <fișier> pentru fiecare rezolvat.
  3. git rebase --continue (dacă erai în rebase) sau git commit (dacă erai în merge).

Dacă te-ai încurcat rău: git rebase --abort / git merge --abort te întorc la starea de dinainte. Nimic pierdut.

Preventiv: branch-uri scurte + sincronizare deasă cu main = conflicte mici și rare.

09 Trusa de urgență

Git aproape nu pierde nimic. Aproape orice greșeală e reversibilă.

SituațieComandă
Am modificat un fișier, vreau înapoigit restore <fișier>
Am făcut add din greșealăgit restore --staged <fișier>
Anulez ultimul commit, dar păstrez modificărilegit reset --soft HEAD~1
Întrerup ce fac și sar pe alt branchgit stash → … → git stash pop
Am șters un commit / branch și îl vreau înapoigit reflog → git checkout <hash>
Anulez un commit DEJA împins pe branch partajatgit revert <hash>
reset vs. revert: reset rescrie istoria — bun local, interzis pe ce ai împins pe un branch partajat. revert creează un commit nou care anulează efectul unuia vechi — sigur pe branch-uri partajate.

git reflog e plasa de siguranță: ține evidența oricărei mișcări de HEAD din ultimele ~90 de zile. Chiar dacă crezi că ai pierdut ceva, e probabil acolo.

10 Reguli de aur

Rezumatul de pus pe perete.

  1. main doar prin PR. Niciun commit direct pe branch-ul principal.
  2. Branch-uri scurte, o intenție per branch.
  3. Commit-uri atomice, mesaj în format tip: descriere.
  4. Pull / rebase des ca să eviți conflicte mari.
  5. PR-uri mici, cu descriere: ce / de ce / cum verifici.
  6. Self-review înainte de a cere review.
  7. Niciun secret în repo. .gitignore de la prima zi.
  8. --force-with-lease, niciodată --force pe ce e partajat.
  9. revert pe partajat, reset doar local.
  10. Când te-ai încurcat: git reflog. Nu ai pierdut nimic încă.
