Formatul unei zile de joi

BlocDuratăConținut
Tutorial60–90 minO capabilitate Claude Code prezentată concret: ce e, unde „locuiește" (ce fișier / config), când o folosești și când NU. Demo scurt pe un repo de test, nu teorie.
Lucru aplicat~90 minFiecare aplică principiul zilei pe repo-ul / task-ul lui real și produce un artefact concret (un fișier care rămâne în repo sau în ~/.claude).
Schimb de practici15–20 minFiecare arată artefactul făcut și spune ce a mers / n-a mers. Se notează în docul partajat „AI Wins & Fails".

De ce arată altfel decât programul general

  • Presupunem competența AI, o exploatăm. Nu explicăm ce e un token sau un prompt bun. Plecăm direct de la: „știi să prompt-uiești — hai să transformăm asta în comenzi reutilizabile, verificabile și partajabile."
  • Fiecare săptămână produce cod / config, nu notițe. La Claude Code, artefactele sunt fișiere reale: CLAUDE.md, un skill, un subagent, un hook, o intrare MCP, un plugin. Ele intră în repo și devin infrastructură de echipă.
  • De la individual la platformă de echipă. Faza 1 = folosire disciplinată. Faza 2 = îți construiești extensii proprii. Faza 3 = le împachetezi, le guvernezi și le automatizezi pentru toată echipa.

Principii de design ale programului

  • Principiul e fix, aplicarea e liberă — subiectul zilei (ex: „subagents") se predă o singură dată, dar fiecare îl aplică pe repo-ul lui, nu toți pe același proiect.
  • Fiecare artefact ajunge sub control de versiune — dacă e bun, se comite. Artefactele bune ale unuia devin standardul echipei în Faza 3.
  • Prezentator rotativ după săptămâna 3 — la o echipă senior, cel mai bun conținut vine din practica cuiva care a descoperit un tipar util. Cine descoperă, prezintă.
  • Unealta se mișcă rapid — Claude Code publică des. /help și docul oficial sunt sursa de adevăr; programul predă principii care rezistă, nu sintaxă care se schimbă săptămânal.

S1

Modelul mental & bucla zilnică făcută bine

Tutorial: de ce majoritatea folosesc Claude Code sub potențial. Plan mode vs. execuție directă, gestiunea contextului (/clear, compaction), alegerea model / effort după sarcină, sistemul de permisiuni allow/ask/deny.

Lucru aplicat: fiecare ia o sarcină reală și o duce cap-coadă folosind plan mode + alegere conștientă de model/effort.

o „rețetă" personală de sesiune: când plan mode, ce model/effort, când /clear
plan modecontextmodel/effort
S2

CLAUDE.md — „constituția" repo-ului

Tutorial: CLAUDE.md e sursa de adevăr pe care Claude o citește la fiecare sesiune. Straturile de memorie (personal ~/.claude vs. proiect .claude) și precedența lor. Ce pui înăuntru și, la fel de important, ce lași afară.

Lucru aplicat: fiecare scrie sau rescrie CLAUDE.md pentru repo-ul lui.

S3

Slash commands & skills — promptul repetat devine unealtă

Tutorial: comenzile custom și skills sunt acum unificate (ambele se invocă /nume). Când e „doar un template de prompt" vs. când e „logică de domeniu cu fișiere ajutătoare". Argumente, allowed-tools, injectarea de context.

Lucru aplicat: fiecare ia un prompt pe care îl scrie repetat manual și îl transformă într-o comandă reutilizabilă.

un slash command / skill funcțional (ex: /review, /commit, /pr)
skillsslash commands

S4

Subagents — izolare de context & paralelism

Tutorial: un subagent e o sesiune Claude separată, cu propriul context window (.claude/agents/). Agenții built-in (Explore read-only, Plan) și când definești unul propriu. Paralelism și tiparul recomandat: subagenți read-only pentru cercetare, Edit/Write rămân la agentul-părinte.

un subagent propriu (ex: code-reviewer, codebase-explorer)

S5

Hooks — reguli deterministe, nu speranțe

Tutorial: hooks sunt scripturi care rulează la evenimente din ciclul de viață (PreToolUse, PostToolUse, SessionStart ș.a.). Diferența față de instrucțiuni în prompt: un hook nu halucinează. Coduri de ieșire care blochează/permit o acțiune.

minim un hook configurat (guardrail sau formatare)
hooksguardrails
S6

MCP — Claude Code vorbește cu lumea din afara repo-ului

Tutorial: MCP conectează Claude Code la servicii externe și la tooling-ul intern (API-uri proprii, baze de date, browser automation). claude mcp add, transporturi stdio vs. SSE. Când merită un server MCP vs. când un simplu script/CLI e suficient.

S7

Plugins — împachetezi tot ca unitate de echipă

Tutorial: un plugin e un bundle versionat care poate livra împreună skills, subagenți, comenzi, hooks, output styles și definiții MCP — instalabil cu o singură comandă /plugin. E modul canonic de a partaja extensii între oameni.

primul plugin de echipă (chiar minimal), într-un repo

Review de fază (10 min): avem deja subagenți, hooks, MCP și un început de plugin. Ce devine „standard de casă" și ce rămâne personal?

Ce înseamnă „fluent în Claude Code"

Toți din echipă sunt deja ingineri seniori — deci matricea nu măsoară seniority, ci maturitatea folosirii uneltei. Cele trei niveluri urmăresc exact fazele programului.

NivelDefinițieFaza
Operator Folosește Claude Code disciplinat ca daily driver: plan mode când trebuie, context curat, alegere conștientă de model/effort, un CLAUDE.md bun și câteva comenzi proprii. Nu îl mai tratează ca pe un chat. Faza 1
Constructor Își construiește extensii proprii: subagenți pentru izolare de context, hooks deterministe ca guardrails, integrări MCP. Știe compromisurile și alege corect. Faza 2
Arhitect de platformă Împachetează totul în plugins pentru echipă, automatizează în CI / prin SDK, stabilește politica de permisiuni și guvernanță, gândește cost/securitate la nivel de sistem și mentorează restul echipei. Faza 3

Matricea e un reper, nu o grilă de evaluare. La o echipă senior, mulți intră deja la nivel „Operator" sau chiar „Constructor" pe unele axe.

Calibrare pentru o echipă care știe deja multe

  • Diagnostic în S0 (30 min, opțional). Înainte de S1, o rundă scurtă: cine folosește deja plan mode / CLAUDE.md / subagenți / hooks / MCP. Rezultatul îți spune ce comprimi.
  • Comasare, nu diluare. Dacă majoritatea sunt deja solizi pe Faza 1, comasează S1–S3 în 1-2 sesiuni și investește timpul câștigat în S7–S9.
  • Traseu „skip-ahead". Cine e deja Constructor poate sări direct la lucru aplicat și veni cu un artefact mai ambițios.

Cum se măsoară că programul funcționează

  • Câte artefacte reale au ajuns sub control de versiune (CLAUDE.md, skills, subagenți, hooks, MCP, plugins) — nu notițe, ci fișiere comise.
  • Cine altcineva decât tine a prezentat un tutorial (semnal de auto-susținere).
  • Cât din „standardul de casă" (plugin + CLAUDE.md de referință) e efectiv instalat și folosit de întreaga echipă la final.
  • Distribuția pe matricea de fluență (Operator / Constructor / Arhitect) la final vs. la început.
  • Câte fluxuri repetitive au fost automatizate (S8) care înainte se făceau manual.

Note de facilitare

  • Ține docul/canalul partajat „AI Wins & Fails" — completat la finalul fiecărei joi, plus link la artefactul comis.
  • Rotește prezentatorul din S4 încolo; tu rămâi backup pe sesiunile tehnice grele (S5 hooks, S6 MCP, S8 automatizare, S9 securitate).
  • Lasă partea aplicată deschisă — fiecare aduce repo-ul / task-ul lui; nu impune un singur proiect comun.
  • Ai mereu la îndemână un repo de test „de nisip" pentru demo-uri, ca nimeni să nu testeze hooks/permisiuni distructive pe cod real.
  • Unealta se schimbă des: la începutul fiecărei sesiuni, un /help + o privire pe docul oficial ca să prinzi ce s-a schimbat.
  • La finalul fiecărei faze (S3, S7, S10), review scurt de 10 min: ce devine standard de casă, ce rămâne personal.
